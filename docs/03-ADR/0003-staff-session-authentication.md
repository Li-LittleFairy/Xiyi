# ADR-0003：员工 Session 登录与固定角色

- 状态：已采纳
- 日期：2026-11-19
- 决定人及依据：用户要求完成“员工登录与身份识别”；一期为本机门店管理应用，已有固定 MANAGER/STAFF 角色和员工账号表。
- 关联记录：ADR-0001、ADR-0002

## 背景与需要解决的问题

收衣、洗护、收款和交付需要可信的当前员工身份，后端必须据此记录经办人并限制店长专属操作。前端隐藏按钮不能充当权限控制。

## 约束与判断标准

- 现阶段在本机浏览器使用，不引入第三方身份平台。
- 密码只保存单向自适应哈希；不在源码或接口响应中保存或返回明文密码。
- 员工停用后不能登录，历史订单仍保留员工引用。
- 当前只有 MANAGER 和 STAFF 两类固定角色，不提前建设动态权限表。

## 备选方案及代价

1. 服务端 Session：浏览器保存会话Cookie，后端维护身份，退出可立即失效；适合当前同源本机应用。
2. JWT：适合更多独立客户端，但需要额外处理撤销、刷新和令牌存储；当前没有相应需求。

## 决定与理由

一期采用 Spring Security Session 登录。业务接口默认要求登录；登录和CSRF令牌端点允许匿名访问。当前员工响应包含员工ID、登录名、姓名和角色代码。

使用BCrypt保存新密码。为兼容已经写入数据库的演示SHA-256哈希，认证器临时允许旧格式匹配，并在首次成功登录时自动改写为BCrypt。此兼容仅用于现有演示数据迁移。

## 后果、限制与需要验证的事项

- 改变数据的Session请求需要CSRF令牌；登录端点单独豁免，避免尚无会话时无法登录。
- 前端后续应先取得 `/api/auth/csrf`，在修改请求中发送返回的请求头。
- 当前未实现登录失败限流、密码修改、找回密码和会话并发数量管理；正式部署前根据访问范围补充。
- 顾客端认证仍未决定，不复用员工账号体系。

## 复议条件与替代记录

若后续正式支持多个独立客户端或跨域公网部署，重新评估会话Cookie、CSRF、跨域和令牌方案，并用新ADR替代本记录。
