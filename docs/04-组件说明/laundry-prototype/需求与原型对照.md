# 需求文件与 V0.3 原型对照

核对日期：2026-10-23。核对对象：当前 `laundry-prototype/dist/customer.js`、`laundry-prototype/dist/store.js` 与界面功能清单。

## 对照依据

1. 《洗衣店管理系统_需求说明书_V1.docx》：文档内标注为 V1.2 领导评审版，状态为“需求讨论稿 · 待评审确认”。以下 FR 编号来自该文件第四章。
2. 《laundry_business_brief_leader_v0.3.docx》：七类基础业务场景和不同经营方式的调研分析。
3. 《laundry_project_conversation_archive_for_codex_2026-10-21.md》：信息来源与阶段性决策的说明。
4. 后续交流：用户要求同时展示顾客端与门店端，展示界面不堆放业务规则待确认内容。

本文描述原型对文档内容的覆盖情况，不把讨论稿或调研候选项升级为已批准的开发要求。“已展示”仅表示有对应界面或模拟交互，不代表已有正式后台能力。

## 总体结论

当前原型覆盖正常业务主流程：顾客提交送洗需求或员工开单 → 实际收衣 → 洗护 → 收款 → 取衣 → 历史与经营查询。七类场景都有相关入口，但部分场景仅覆盖正常流程，异常处理和管理操作不足。

“顾客端 6 个界面、门店端 9 个界面”是页面数量，不代表需求已逐条覆盖。尤其客户管理、员工账号、项目维护等页面，目前功能比名称所暗示的范围更窄。

## 一、管理端需求逐项对照

| 来源 | 当前展示 | 覆盖程度与缺口 |
| --- | --- | --- |
| FR-01 登录与权限 | 页面显示固定店长身份；设置中可添加员工姓名、启停员工 | **未展示角色使用差异**。没有登录、退出、老板/员工切换，也没有不同角色可见页面和操作差异；员工启停不影响登录或权限。 |
| FR-02 客户管理；3.1 收衣接待 | 开单填写姓名手机号；客户列表汇总历史订单，可跳转查看 | **部分覆盖**。没有独立新增/编辑客户，没有收衣时检索并选择已有客户的操作；客户页本身没有搜索。 |
| FR-03 收衣开单 | 衣物项目、件数、颜色/瑕疵、费用、预计取衣日期、订单号；支持确认顾客预下单 | **主要覆盖**。同项目衣物会合并数量和状况描述，不能清楚标识“同类两件中具体哪一件破损”；衣物类别和洗护项目也未分别建模展示。 |
| FR-04 订单查询与管理 | 按订单号、姓名、手机号、状态查询，查看详情；预下单收衣时可核对数量和状况 | **部分覆盖**。没有正式收衣后的改单、取消入口，也没有取消原因和已取消状态。收衣核对不等于通用改单。 |
| FR-05 洗衣进度；3.2 洗衣任务 | 待洗护 → 洗护中 → 待取衣 → 已完成 | **主流程覆盖**。没有处理中补写异常备注的入口；开单备注不能代替处理过程中新增异常记录。 |
| FR-06 收费记账；3.3 费用核对 | 待取衣时登记一次性全额付款，显示收款方式、付款状态和收款流水 | **部分覆盖**。收款入口仅在待取衣环节，缺少文档讨论的收衣时付款路径。经办人固定使用演示姓名，未展示账号关联；收款流水未单列经办人。 |
| FR-07 取衣交付 | 待取衣订单核对衣物、付款后确认交付，记录处理经过，完成后退出待取列表 | **主要覆盖**。取衣页没有直接搜索框，需要先在订单列表搜索再进入取衣。 |
| FR-08 经营管理；3.5 老板管理 | 今日数据、累计实收、近七日图表、收款流水；改价、添加/启停员工 | **部分覆盖**。没有按日期范围查询订单/收款；项目只能改价，不能新增或停用项目；员工管理未形成完整账号操作。 |
| FR-09 操作记录；3.6 订单追溯 | 详情直接显示创建、收衣、状态、收款、交付记录 | **部分覆盖**。没有改单/取消及修改前后内容；未展示“管理员按需展开、员工不可见”的交互。 |
| 第五章数据留存、7.1 数据恢复、第六章设置页 | 浏览器保存演示数据 | **未展示**本地备份/恢复入口；浏览器保存数据不能代替业务备份恢复。 |

文档中收款时点、改单权限、取消条件等具体规则仍需讨论。当前需要指出的是相应业务路径缺失，而不是在此决定具体规则。

## 二、七类业务场景覆盖

| 场景 | 当前原型情况 |
| --- | --- |
| 客户识别与接待 | 普通客户信息与历史可见；已有客户选择、独立维护不足；无会员身份展示。 |
| 下单与实际收衣 | 同时展示顾客预下单和员工直接开单，并区分实际收衣，覆盖较清楚。 |
| 费用计算与结算 | 有标准计价和线下一次性收款；只有取衣时付款；无会员额度消费。 |
| 洗衣处理与质检 | 有正常洗护状态流转；无处理中异常记录；无独立质检流程。 |
| 取衣核对与交付 | 有衣物、付款核对和整单交付。 |
| 历史查询与异常处理 | 历史查询已展示；改单、取消及异常处置路径缺失。 |
| 日常经营与规则管理 | 有统计、改价、员工列表；缺日期查询、项目维护、角色差异与备份入口。 |

## 三、调研中提过，但当前没有展示的候选能力

- 会员姓名/卡号、余额或剩余次数、充值、消费扣减与额度流水。
- 合作企业发放福利额度、额度来源和有效期。
- 独立质检、重洗、损坏赔偿、退款、部分付款、混合支付、分批取衣。
- 瑕疵照片、打印凭证、扫码、通知提醒、导出、利润、多终端、多门店。

这些并非全部遗漏的首版必做功能。V1.2 第 8.2.2 节和业务调研稿明确将其列为候选场景或后续讨论内容。当前顾客端是普通顾客送洗与查询展示，不能称为会员/次数消费方案。

## 四、原型比原管理端草稿增加的内容

V1.2 原文暂定“顾客参与门店业务，但不登录系统”，顾客端/线上预约在候选功能中。当前增加了顾客首页、服务选择、自助送洗、个人订单和个人信息，这来自后续调研与用户“两端都展示”的明确要求；该要求确认了原型展示方向，未确认正式系统的产品形态和开发范围。

“拾净洗护”品牌、示例项目价格、示例客户和员工是演示设计内容，不能当作领导提供的业务数据。

## 五、下一版原型建议

优先补齐已有业务叙述中的操作：老板/员工身份展示、已有客户选择、改单/取消、洗护异常备注、收衣时收款。随后补齐项目维护、日期查询、按需查看操作记录和备份恢复界面。

这些操作大多可以融入现有页面或弹窗，无需大幅增加一级菜单。会员、次数消费、企业额度等另作展示范围讨论，不因它们在调研文档中出现就自动全部加入。
