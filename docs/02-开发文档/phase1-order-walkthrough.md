# 一期基础流程与数据推演

日期：2026-11-19。

用户已明确“先实现基础的，后续可以二期”。本文按此方向推演普通到店订单，是业务与数据设计草案；表结构和下述具体规则尚未整体定稿。本次没有创建数据库或实现接口。

## 1. 推演范围

先推演门店员工现场开单，客户无需登录；保留已有顾客端原型，顾客账号和自主下单是否随一期实现另行明确。不能据此认为用户取消了双端展示要求。

建议的基础流程：员工登录、客户查询与登记、项目价格维护、逐件收衣、整单洗护、线下收款登记、整单交付、历史与实收查询。配套包含操作记录、必要异常备注、后端权限、防重复、备份恢复。

本轮采用的规则假设：

- 同一次送洗对应一张订单，每件可识别衣物对应一条明细，每条暂选一个洗护项目。
- 费用使用标准价格，没有折扣、抹零或临时改价；保存成交价格和项目名称快照。
- 可在收衣时或取衣时一次付清；本轮收款仅记录门店实际收到的现金或线下电子付款，不调用支付网关。
- 洗护按整单流转，交付要求洗好并付清；交付前核对全部衣物。
- 会员储值、次数、企业额度、分次收款、分批取衣、单件工序等先列二期候选，不是二期必做承诺。

## 2. 七张核心表的职责

| 表 | 职责与关键关联 |
| --- | --- |
| staff_account 员工账号 | 保存店长/店员账号、密码哈希、固定角色、启停状态；经办字段引用账号，停用不删除历史引用 |
| customer 客户 | 保存联系方式和备注；订单通过 customer_id 关联；手机号先用于检索，不未经业务确认就设为唯一身份 |
| service_item 洗护项目 | 保存当前项目名称、标准价格、启用状态；一期示例为具体可收费项目，例如外套清洗 |
| laundry_order 订单 | 保存订单号、客户ID、联系信息快照、状态、应收金额、预计取衣时间、收衣人及时间、交付人及时间、并发版本等 |
| order_item 订单衣物 | 通过 order_id 关联订单，保存单内序号、类别、颜色、瑕疵、服务ID、服务名称及成交价格快照；一期逐件登记 |
| payment_record 收款 | 关联订单、实际金额、方式、收款时间、经办人和幂等标识；当前仅保存已确认的实际收款 |
| order_event 订单操作记录 | 关联订单、操作人、操作类型、时间、原因和必要前后值；包括异常备注，按权限查阅 |

订单单独保存成交应收总额，服务端负责使其与明细合计一致。基础方案以收款记录作为已付依据，接口可返回付款状态及已收金额，不要求再维护一份可独立修改的付款布尔值。

待确定数据库后再落地字段类型、外键、索引和约束。暂不设计大而全的权限配置表、通用字典表或经营汇总表。

## 3. 推演一笔订单

以下均为虚构数据，金额单位为元。日期用“第1天、第2天”表示。

### 准备基础数据

- 员工 E01：林晓，店长；员工 E02：小陈，店员。
- 项目 S01：外套清洗，40 元；S02：羽绒服清洗，68 元。

### 第1步：接待客户

第1天，小陈用手机号查询客户，核对姓名后选择已有记录；若无匹配则登记演示客户 C01“张女士”。已存在客户不重复新增。同一手机号出现多条记录时让员工核对选择。

新增数据（新客户示例）：customer 1 行。

### 第2步：收衣开单

创建订单 O01，联系信息保存本次快照，预计第3天取衣；实际收到以下3件衣物。

| 明细 | 订单 | 衣物 | 颜色 | 原有瑕疵 | 项目 | 成交价 |
| --- | --- | --- | --- | --- | --- | --- |
| I01 | O01 | 外套 | 米色 | 袖口破损 | S01 | 40 |
| I02 | O01 | 外套 | 黑色 | 无明显瑕疵 | S01 | 40 |
| I03 | O01 | 羽绒服 | 白色 | 领口污渍 | S02 | 68 |

订单应收 148 元，状态为待洗，收衣人为 E02，付款情况为未付款。

一次保存：laundry_order 1 行、order_item 3 行、order_event 1 行（收衣开单）。订单、明细和此操作记录应在同一事务保存，失败时不留下半张订单。重复开单请求需要防止生成重复业务。

### 第3步：开始洗护

小陈点击开始洗护，服务端检查权限和当前状态，将订单从待洗变为洗护中，追加操作记录。更新状态和操作记录一起提交。

明细中的颜色、破损和成交价不变；本轮没有独立工序和任务分配表。

### 第4步：完成洗护

第2天，小陈确认洗好，订单变为待取衣，追加操作记录。若存在未解决的问题，不继续正常交付，可先追加异常备注。本轮异常备注用于留痕，不宣称已实现完整返工、赔偿流程。

### 第5步：登记收款

张女士到店，林晓确认线下实际收到 148 元，选择现金或线下电子支付并提交。

新增 payment_record 1 行：订单 O01、金额148、实际收款时间、经办人E01、方式和防重复标识；同时追加 order_event 1 行。

服务端在事务内重新核对订单状态、应收和现有收款，拒绝不符合一次付清规则的金额。基础方案中每张订单最多一条实际收款记录，可用订单关联的唯一约束配合幂等处理防止并发重复收款；请求重试返回已有结果，不追加第二笔。

收款后订单仍是待取衣。实收查询依据 payment_record 的收款时间汇总，第1天开单不等于第1天收到148元。

### 第6步：核对交付

林晓核对客户、三件衣物和付款，确认交付。服务端检查订单为待取衣、已付清后，将订单更新为已完成，保存交付人E01及交付时间，追加操作记录。

再次点击交付不会覆盖原交付人/时间或新增一次交付。并发修改通过事务与条件更新或版本检查处理，不能只靠按钮禁用。

## 4. 验证分支与基础异常

| 场景 | 建议行为 | 数据影响 |
| --- | --- | --- |
| 收衣时付清 | 开单后即可收款；之后照常洗护，取衣不再收款 | 收款时间在第1天，付款不改变洗护状态 |
| 项目涨价到78元 | 新订单使用新价格，O01仍为148元 | 改项目标准价，不重算历史明细 |
| 未洗好要求取衣 | 拒绝交付，明确当前状态 | 不变更订单，不产生成功交付记录 |
| 未付清要求交付 | 按本轮假设拒绝交付 | 引导收款，不假造已付款 |
| 待洗且未付款，开单填错 | 建议允许有权限者修改，要求理由并校验版本 | 更新明细与总额，同时保存必要前后值；保留追溯信息 |
| 待洗且未付款，客户取消 | 建议允许取消并填写原因 | 标记已取消，保留订单与明细，不产生收款，禁止后续正常流转 |
| 已付款后要改单或取消 | 不能沿用未付款取消路径；本轮草案阻止该操作 | 如一期需要实际处理，必须把退款或调账的记录及规则纳入一期，不能删除原收款冒充退款 |
| 洗护中发现问题 | 追加异常备注并保留经办人与时间 | 使用 order_event 记录；返工、损坏和赔偿如何闭环需另定规则 |
| 两人同时改单/收款/交付 | 服务端检查当前记录，拒绝冲突或返回已有结果 | 数据库约束和事务保证只产生有效的一次结果 |
| 员工停用 | 禁止其继续执行后续操作，保留旧业务引用 | 不删除员工及历史操作记录 |

已付款取消和洗护中异常是草案的真实限制：若实际门店高频发生，相关处理不能只因计划“二期”就忽略。本机开发演示可明确只覆盖上述受限路径，正式业务使用前须确定处理办法。

## 5. 本轮推演的设计结论

1. 普通到店、一次付清、整单流转的流程可由七张核心表表达。
2. 一件一条明细能识别瑕疵，但不要求一件一套洗护工序。
3. 成交价格和联系信息需要历史快照；价格调整不会改变历史订单。
4. 收款与洗护进度独立，收款记录是实际已付的依据。
5. 基础权限、幂等、数据一致性与备份恢复属于本期质量要求，不因功能分期而省略。
6. 顾客真实登录、自助预下单若进入一期，需要增加或明确账号模型、订单归属和待收衣流程；不能拿手机号查询代替身份认证。
7. 分次收款若进入二期，需要修改一次付清相关约束、接口和验收；没有必要现在就提前实现该能力。
