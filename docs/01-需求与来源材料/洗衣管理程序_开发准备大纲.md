## 一、当前起点

已有业务调研、需求初稿、顾客端和门店端原型，以及功能覆盖差异清单。原型可以模拟主要业务流程，但数据保存在浏览器，没有正式后台、身份认证和真实支付。

下一步重点是明确第一版做什么，并把核心业务写到足够支持实现和验收的程度。现有原型可继续作为界面参考；正式系统的数据、权限和流程需要由后端管理。

## 二、开发前先明确的五件事

| 事项 | 需要得到的结论 | 对开发的影响 |
| --- | --- | --- |
| 使用场景 | 普通商业洗衣店、企业洗衣服务，还是用于研发实践的演示项目 | 决定业务重点、验收对象与交付标准 |
| 使用端与人员 | 店长、店员、顾客分别使用哪些能力；顾客端是否进入首版 | 决定账号、权限和页面范围。“两端展示”不自动等于“两端正式上线” |
| 部署与访问 | 门店单机、局域网多设备，还是顾客通过外网访问 | 决定部署方式、联网条件和数据访问方式；当前同页切换无法证明跨设备可用 |
| 结算方式 | 普通收款、储值、次数或企业额度；仅登记线下付款还是对接支付 | 决定账户、收款和消费记录设计。如果实际业务以次数为核心，应先明确次数规则 |
| 首版边界 | 必须完成哪些流程、哪些暂缓、谁来验收 | 防止把全部调研候选功能直接当作开发任务 |

如暂时没有业务结论，可以为技术验证写明临时假设及其影响；不要把假设记录为正式决定。

## 三、把七类场景整理成可执行需求

每个场景用同一套简短格式描述：谁操作 → 从哪里进入 → 输入什么 → 满足什么条件 → 保存什么 → 状态如何变化 → 失败或异常如何处理 → 怎样验收。

重点补充以下规则：

1. 客户与账号：客户如何识别和去重；员工账号与客户档案分开；若有顾客端，如何登录并限制其只能访问自己的信息。
2. 收衣：衣物类别、洗护项目、件数、颜色和瑕疵如何记录；同类多件衣物中有一件破损时如何识别；预计取衣时间如何填写。
3. 计价：价格由谁维护；订单保存成交单价，后续调价不改变历史金额；明确是否支持折扣或临时改价。
4. 状态：若包含顾客自助下单，区分待收衣与已收衣；写清允许的状态变化、操作人员和必要前置条件。
5. 收款：在哪些环节收款；能否分次收款；记录金额、方式、时间和经办人；如何防止重复记账。
6. 交付：什么状态可以取衣；是否必须付清；如何记录交付人员和时间并阻止重复交付。
7. 改单、取消与异常：什么阶段允许操作，是否需说明原因；已收款订单取消如何处理，不能只有取消按钮而没有款项处理路径。
8. 经营查询：订单按哪个日期查询，营业实收按哪个日期统计；员工与店长分别能看什么。

原型已发现的缺口包括登录角色差异、已有客户选择、改单/取消、洗护异常备注、收衣时付款、日期查询、项目维护和备份恢复。按首版范围筛选后补齐对应页面或弹窗。

## 四、最少准备五份材料

无需写五本长文档，可以放在一个项目文档目录中，以短表格为主。

| 材料 | 最少需要的内容 | 完成标准 |
| --- | --- | --- |
| 首版范围与决定记录 | 纳入/暂缓功能、适用场景、决定人、日期、仍存假设 | 知道本版做什么以及依据 |
| 页面与功能清单 | 页面、操作、字段、权限、结果，对应需求编号 | 原型入口能对应到业务动作 |
| 业务规则与状态图 | 收衣、计价、收款、状态流转、改单取消、交付 | 核心操作不需要开发时临时猜规则 |
| 数据与接口草案 | 核心实体关系、主要字段、接口输入输出和权限 | 同一业务概念前后端含义一致 |
| 开发任务与验收清单 | 按业务流程拆任务，写明验收步骤和预期结果 | 每完成一项，都能演示和检查 |

## 五、技术准备方向

沿用此前倾向，先按 Java + Spring Boot + 简单前端考虑。具体版本、依赖组合在搭建时检查兼容性后固定。

- 后端先采用一个应用，按账号、客户、项目价格、订单、收款、统计等业务组织代码。
- 前端依据现有 HTML/CSS/JavaScript 原型评估复用；页面展示可参考，浏览器内模拟数据和权限不能直接当作正式实现。
- 数据库先依据部署和并发访问方式选择；本机轻量使用可评估 SQLite，需要多人或多设备访问时再评估相应数据库方案。
- 开发环境准备 JDK、构建工具、编辑器、Git；是否需要 Node 取决于前端构建方式。
- 建立独立开发目录并保留展示原型；配置与密码分离，演示数据与正式数据分开，提供明确的初始化和启动步骤。
- 搭建时先验证最小链路：打开页面 → 请求后端 → 写入数据库 → 重启后查询到数据。

### 核心数据概念（草案，尚不是最终建表方案）

员工账号与角色、客户、洗护项目、订单、衣物明细、收款记录、操作记录。收款与订单分别记录，并通过订单关联；支付方式与洗衣状态分开。若确认会员或企业额度业务，再设计对应账户和消费流水。

在正式实现时，金额计算、权限检查、状态变更、收款防重复必须由服务端保证；订单修改和对应操作记录应一致保存。

## 六、建议实施顺序

| 阶段 | 工作 | 阶段完成标志 |
| --- | --- | --- |
| 1. 范围与关键交互 | 明确首版，补齐首版涉及的原型缺口 | 能用一笔具体订单讲清正常与必要异常流程 |
| 2. 工程与基础数据 | 建工程、数据库、登录角色、客户及洗护项目基础能力 | 能登录，并保存、查询基础数据 |
| 3. 第一条真实业务流程 | 员工开单 → 洗护 → 收款 → 取衣 → 历史查询 | 使用真实数据库跑完一笔订单，重启后数据仍在 |
| 4. 管理和异常 | 实现纳入范围的改单、取消、异常记录、权限、统计与备份恢复 | 正常和错误操作均有明确结果，金额可核对，备份可恢复 |
| 5. 顾客端及结算扩展 | 若首版包含顾客端，接入登录、个人订单、实际收衣同步；会员等按已确认范围实施 | 不同用户数据隔离，实际目标设备可访问 |
| 6. 交付验证 | 打包、初始化、安装启动说明、验收演示 | 在目标环境完成安装和整套业务验收 |

以上顺序以共用门店订单流程为基础；如果会员/企业额度是业务核心，其需求与数据设计应在阶段 1 明确，相关结算随阶段 3 一起实现，不能到最后才补设计。

## 七、先写好的核心验收例子

- 开单记录两件同类衣物，其中一件有破损，后续能准确核对到对应衣物。
- 调整服务价格后，之前订单的成交金额保持不变。
- 未付款订单不进入实收统计；收款归入实际收款日期。
- 连点或重复请求不会产生重复收款、重复交付。
- 不符合状态或付款条件的交付被拒绝，并给出明确原因。
- 员工不能通过直接调用接口执行店长专属操作。
- 若包含顾客端，顾客无法通过修改订单编号访问他人订单。
- 订单更新失败时不会留下与订单矛盾的操作记录；取消与款项处理符合已确定规则。
- 重启后记录保留，使用备份可以恢复并核对关键业务数据。

## 八、如何配合 AI 开发

每次给 AI 一个可验收的小任务，附上相关需求、原型、规则和预期结果。例如：“实现收衣开单，保存客户、衣物明细和成交单价，成功后能够在列表查到订单。”

每个任务依次完成：说明实现范围 → 实现 → 检查与必要测试 → 演示结果 → 提交代码。由你检查业务含义、实际操作和数据结果；发现新业务问题时记录并修订需求。避免在开发过程中让模型自行扩充首版范围。

## 九、现在先做什么

下一份最值得完成的材料是《首版开发范围与核心流程》：用一页范围表和一笔订单示例，明确使用场景、使用端、结算方式、部署方式和验收目标。已有结论直接记录，未确定的标明临时假设及影响。

随后补齐该范围对应的原型操作，并整理数据与接口草案，再搭建工程。无需等全部远期功能讨论完才能做技术验证，但正式业务实现应有明确的规则依据。
