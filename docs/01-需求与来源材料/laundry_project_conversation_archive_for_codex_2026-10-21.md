## 0. Codex 首先要知道的 10 件事

1. 这个项目源于用户刚入职时（2026 年 7 月底）领导陈总提出的一个小任务：做一个洗衣管理程序，要求尽量**全程使用 AI**，先了解业务、整理需求、找时间评审，再开发并跑通。
2. 当时记录非常零散，原始关键词包括：**洗衣程序、面板、记账、美萍洗衣管理、数量、人员、瑕疵、费用、来取衣服、单机版、什么平台做、全程 AI、产品原型**。目前无法确认陈总心目中的确切产品形态。
3. 已针对普通中小洗衣门店形成过以“**老板/店长 + 员工**”为两类系统账号的初版需求。后来又了解到一种现有的**企业洗衣会员卡/按次数消费**场景，因此补充调研了会员、充值、顾客自主下单等模式，但**未决定本项目必须实现会员端或积分系统**。
4. 重点不是“仿照公司现有小程序”：用户明确表示**没有源码，陈总也没有直接指示照着它做；只是参考真实业务，让调研更全面，然后找陈总确认**。
5. 需求分析主线已确定：**使用者 → 真实业务场景 → 业务行为与信息 → 推导功能 → 找出业务规则和异常 → 业务方评审 → 决定首版范围**。
6. 基础洗衣业务被归纳为 **7 类场景**：客户识别与接待、下单与收衣、费用计算/消费记账、洗衣处理、取衣核对与交付、历史查询与异常、经营及日常管理。
7. **顾客下单 ≠ 店员已收到衣服**；提出将“下单”和“确认收衣”分成两个业务动作。默认订单进度的候选路径：已下单 → 已收衣/待洗 → 清洗中 → 待质检 → 待取衣 → 已完成。但质检是否单独做、按整单还是单件更新，均未确认。
8. **会员身份 ≠ 支付方式**。会员可以不充值而现金/电子支付；会员也可能自行充值或通过合作企业获得余额/次数/积分。不同结算方式可共用订单流程，但单位、扣减与返还规则尚待确认。
9. 用户希望首版**功能少而完整**，先跑通洗衣业务闭环；“后续可扩展”是设计原则而非立刻建设复杂功能。
10. 用户希望使用 **Java 17 + Spring Boot/Spring MVC + Service + MyBatis（或 MyBatis-Plus）+ SQLite + 简单 HTML/CSS/JavaScript** 实现本地 Web 管理系统；这是**技术倾向/初步建议**，不是正式拍板的架构。AI 研发方面希望从常规 AI 辅助，逐步尝试 Skill/Workflow/Agent，并沉淀经验，但尚待确认是否属于领导要求的正式交付。

## 3. 已形成的业务调研框架：7 类基础场景

下表中“系统能力”仅指根据业务场景**可能需要**的功能，不等于首版开发清单。

| 场景 | 典型业务叙述 | 参与者 | 需要了解/记录的信息 | 候选系统能力 | 主要未确认点 |
|---|---|---|---|---|---|
| S1 客户识别与接待 | 顾客到店，工作人员识别老客户、新客户或会员 | 顾客/会员、洗衣员工 | 姓名、手机号、会员编号、账户信息 | 客户查询/创建、会员身份识别、历史记录 | 普通客户是否必须注册？会员是否独立登录？公司合作员工是否自动开通？ |
| S2 下单、收衣检查与开单 | 顾客提交洗衣需求或直接到店；工作人员实际清点并接收衣物 | 顾客、洗衣员工 | 衣物种类、数量、颜色/特征、瑕疵、服务、预计取衣日期 | 下单、确认收衣、订单编号、衣物明细和瑕疵记录 | 客户自助下单还是员工开单？已下单/已收衣是否单独区分？收衣凭证或照片？ |
| S3 费用计算、支付与消费记账 | 根据服务类型/数量生成应收金额或扣减会员额度 | 顾客/会员、收款员工、管理员 | 服务价格/消耗规则、应付/实付、交易编号、次数/积分余额、来源 | 价格规则、现金/电子支付、预存/次数支付、消费记录 | 何时扣费？一次付清/部分付款？额度不足怎么处理？不同支付方式优惠吗？ |
| S4 洗衣处理与进度跟踪 | 员工查看待洗任务、清洗、必要时质检、准备交付 | 洗衣员工 | 处理阶段、经办人、时间、异常描述 | 订单状态更新、异常备注、可取状态 | 整单或单件更新？质检独立存在吗？重洗/损坏规则？ |
| S5 取衣核对与交付 | 顾客凭手机号、订单编号等查询，核对并领回衣物 | 顾客、洗衣员工 | 订单、衣物、已结算情况、实际取衣时间、经办人 | 查询、费用提示、确认交付、取衣记录 | 客户确认还是员工确认？允许代领/分批领取/欠款取衣吗？ |
| S6 历史查询与异常处理 | 需要追溯费用错误、状态误改、衣物损坏等 | 顾客、员工、管理员 | 历史订单、交易、状态变更、操作人和时间 | 历史查询、关键操作日志、异常处置 | 退款、额度返还、赔偿、权限与变更审批？ |
| S7 经营和日常管理 | 管理员维护服务、价格、人员及经营情况 | 负责人/管理员 | 订单量、收入/次数消耗、员工、价格、服务、备份 | 经营面板、账号、服务价格和规则配置、备份 | 是商业老板还是企业洗衣负责人？按营业额还是福利额度考核？ |

### 3.1 业务闭环与订单节点

**基本洗衣业务闭环**（讨论版）：

客户识别 →（顾客下单/员工开单）→ 员工实际收衣并核对 → 计算费用并按约定时点结算 → 洗衣处理 → 待取衣 → 确认交付 → 经营查询/历史追溯。

注意：**支付不固定在单一节点**，有可能发生在送衣或取衣时；会员额度扣减时点也需要明确。不要把收款状态和洗衣流程状态写成一个字段。

### 3.2 关于“下单”与“收衣”的重要区分

- **顾客自主下单**：只是提交需求，可能还未把衣物交到门店。
- **确认收衣**：门店工作人员已经核对并实际接收衣物；此时数量、瑕疵、洗护项目可能需要确认或修正。
- **柜台员工直接开单**：可以在一次操作中录入订单并确认收衣，但业务含义仍是两个不同动作。
- **尚待确认**：系统最终要不要顾客端；是否支持两种开单方式；顾客提交订单后谁有权更改、确认、取消。

### 3.3 建议的订单进度（仅候选）

| 阶段 | 业务含义 |
|---|---|
| 已下单 | 顾客已提交需求；是否已收衣尚未确认 |
| 已收衣/待洗 | 门店已接收并核对衣物，等待处理 |
| 清洗中 | 正在处理衣物 |
| 待质检 | 清洗完成、等待检查（是否独立设此环节待确认） |
| 待取衣 | 衣物可以交付 |
| 已完成 | 已完成取衣交付 |
| 已取消/异常 | 非正常路径，规则尚待明确 |

**“清洗完成”不等于“订单已完成”**：用“已完成”表述整个订单完成时，必须明确是衣物已交付而非仅洗净。按整单与按衣物单件更新状态仍待确认。

## 4. 会员、普通顾客、合作企业：业务模式统一认识

### 4.1 三个正交维度

1. **客户身份**：普通客户、已注册会员、企业合作发放权益的会员等。
2. **账户/额度来源**：无预存、个人充值、合作企业/公司发放、其他待定。来源不同可记录，但不必天然变成不同类型的用户账号。
3. **付款/消费渠道**：现金、微信/支付宝等直接支付，会员储值金额支付，按次数/积分扣减，或必要时补差等（具体规则待确认）。

**重点**：会员身份 ≠ 一定充值 ≠ 只能用会员账户支付。可以存在“已经办会员，但不充值、仍然每次现金付款”的情况。

### 4.2 次数、积分与金额

- 按次数、按积分可共同归入“会员可消费额度”这一类业务概念，但单位和换算规则不可直接混合或默认完全相同。
- 从公司现有模块观察到：例如“羊毛衫 干洗 2次 ×3”，用户推测可能是每件扣2次，3件总共扣6次；**这只是推测，未证实计算规则。**
- 充值来源可以是本人，也可能是合作公司给其员工统一分配福利额度。是否需要企业合作方管理模块，待确认。
- 余额不足：用户提出充值或现金支付作为可行策略；是否允许充值+现金混合支付、是否允许后付，均需业务方决定。
- 充值最低起充、会员支付折扣、现金与会员权益差别：用户提出作为合理商业方案，但**是否存在及具体数值没有业务依据，不能直接写为既定规则**。
- 年度额度是否清零、结转，以及退款后退回哪一类额度，需进一步定义。

### 4.3 会员端是否存在

“门店系统保存会员账户”不代表“会员必须有登录端”。至少有两个方案：

- 只做门店端：员工根据手机号/会员卡号查询余额、创建订单、处理费用；会员没有独立登录界面。
- 门店端 + 会员端：会员可以看余额、充值、消费、订单和取衣状态，甚至自助下单。

**当前没有决定选哪个方案。** 若最终要求会员手机访问，则要重新明确单机版、联网、部署和鉴权等约束。

### 4.4 公司现有会员卡模块：已观察信息

带教老师展示的是**使用者面板**，不是后台，也没给源码。观察到：

- 顶部：会员姓名、会员卡号、剩余次数。
- 分区：支付记录、充值记录。
- 单条支付记录：交易单号、衣物和洗护方式（举例“羊毛衫 干洗 2次”）、`×3` 数量、使用次数、支付时间、是否取走、预计取衣时间。
- 页面底部有“确认订单”按钮；**不确定其行为是确认下单、收衣、支付还是取衣**。
- 业务背景：公司员工可在楼下洗衣房送洗，消耗每年预先充值/分配的额度。

**用户明确意见**：这个既有系统是可以借鉴的现实场景，但**不是要照搬它，也不是陈总已指定目标**。

## 6. 业务规则与需要业务方拍板的问题

下述为**评审重点**，并非全部需要在第一次沟通逐项提问。给领导的调研汇报应先说做过什么和分析结果，再集中呈现少量关键问题，不要到处堆叠问号。

### 6.1 最重要的 6 组确认事项（优先确认方向）

1. **项目定位**：陈总真正希望做商业洗衣店管理、企业内部福利洗衣、现有系统管理端，还是 AI 全流程练手项目？“单机版”仍是硬约束吗？是否有真实投入使用的目标？
2. **使用者/角色**：只有管理员与洗衣房员工，还是会员也要登录、自助查询/下单？合作企业是否需要操作入口？
3. **开单/确认收衣**：顾客自助下单、员工柜台开单，还是二者兼容？什么时点算已正式收到衣服？
4. **支付/会员制度**：直接付费、充值金额、积分/次数、企业额度哪些适用？何时扣减、如何退款、余额不足和优惠怎么处理？
5. **洗衣/取衣流程**：整单或单件跟踪？需要质检吗？取衣由谁确认？异常如何记录？
6. **首版范围和 AI 成果**：第一版最小闭环是什么？只验收软件还是也希望总结 AI 使用流程、Skill/Agent 等实践成果？

### 6.2 较细的确认项（在方向明确后再讨论）

- 收衣时付款与取衣时付款是否都支持；能否欠款取衣。
- 会员是否可以不充值直接支付；会员优惠规则是否存在；最低起充是否存在。
- 合作企业是否批量开通账户、发放年度额度、额度过期/结转。
- 门店是否需要实体小票/收衣凭证、衣物照片、订单扫码。
- 质检是否必须单独操作；清洗异常、重洗、损坏赔偿如何处理。
- 分批取衣、代领、部分付款、退款、积分返还是否常见且需要首版支持。
- 本地安装包、双击启动、开机即用、备份恢复方式及负责人。

### 6.3 评审的正确产出

正式评审不是“领导回答所有脑暴问题”，而是至少明确：

- 核心目标与实际业务对象；
- 使用者、业务闭环与关键规则；
- 第一版**必须有**和**暂不做**的范围；
- 需要继续调研的未知项及负责人；
- 后续原型设计、技术方案、验收口径的依据。

## 7. 技术实现与“全程 AI”的讨论（暂定，不等于项目决策）

### 7.1 用户希望采用的 Java 技术方案

- Java 17，Spring Boot + Spring MVC；Controller → Service → Mapper（MyBatis / MyBatis-Plus）→ SQLite。
- 前端尽量简单：HTML + CSS + JavaScript，通过 HTTP/JSON 调用后端 API；可以放在同一个 Spring Boot 项目的 `resources/static`。
- Maven 构建；优先单体项目、本地运行，方便理解完整前后端交互与部署。
- 业务上区分客户/订单/衣物明细/支付记录；核心规则集中处理，避免写死在 Controller 中。
- Spring Boot 是应用启动入口；Spring MVC 提供 HTTP 请求路由，二者无需作为两套独立应用分别启动。
- SQLite 适合本地单机文件数据库，但最终仍须根据运行/并发要求确认；MyBatis-Plus 与 SQLite 的部分方言/功能需验证。

### 7.2 AI 全流程理念

用户过去主要用 **普通 AI 辅助开发**，对 **Skill/Workflow** 和 **Agent** 接触较少，希望借此次项目实践：

| 方式 | 定义/在本项目中的可能用途 |
|---|---|
| 对话式 AI 辅助 | 按阶段与 AI 讨论，生成/修改需求、原型和代码，人工落地与验证 |
| Skill/Workflow | 把重复的接口设计、代码检查、测试步骤沉淀成可重复执行的规范与流程 |
| Agent | 在明确定义目标和权限前提下，让 AI 连续读取仓库、修改代码、运行测试、修复问题并报告变更 |

期望的探索性成果：可运行软件 + AI 参与过程中的方法、效率与局限总结；**但领导是否明确要求第二类成果仍待确认**。人工仍需负责业务确认、审查、测试和验收。

### 7.3 可扩展性与不过度设计

用户特别提出“**地基要打好，给后续迭代留余地**”。讨论结论：

- 第一版做小，先跑通业务；不是提前实现所有猜测的功能。
- 业务职责清楚、订单与衣物明细分开、收款/额度交易单独留痕，后续才容易扩展。
- 权限可先两类固定角色，不必预先做高度复杂的角色/权限配置后台。
- 不为不确定的未来需求引入微服务、消息队列等过度复杂设施。
